Motrix Server ships a `compose.yaml` that works with Docker Compose directly and with the "Project" import feature found in NAS interfaces like Synology Container Manager and fnOS. There is no local build, fixed container name, privileged mode, or host-specific Docker behavior — drop it in, set a few environment variables, and the service starts with a read-only root filesystem and a non-root user.

## Prerequisites

- Docker Engine with the Compose plugin (v2), or Docker Desktop
- A NAS, home server, or VPS running `amd64` or `arm64` (64-bit only; 32-bit ARM is not supported)
- Two writable host directories — or named volumes — for application data and downloads
- The externally reachable URL of the Web UI (required for remote CLI/agent pairing)

## Quick Start with Bind Mounts

The included `compose.yaml` uses bind mounts, making downloaded files visible as ordinary host directories and easy to include in your existing backup strategy.

<Steps>
  <Step title="Create and own the mount directories">
    Create the host directories and set their numeric ownership to match the UID and GID the container will run as. The Compose file defaults to `1000:1000`; replace `id -u` / `id -g` with explicit values if you use a dedicated service account.

    ```bash
    mkdir -p motrix-data downloads
    export MOTRIX_UID="$(id -u)"
    export MOTRIX_GID="$(id -g)"
    chown "$MOTRIX_UID:$MOTRIX_GID" motrix-data downloads
    ```

    Use `sudo chown` if the current administrator does not own the directories. Never set the runtime UID to `0` or enable privileged mode just to bypass a mount permission error.
  </Step>

  <Step title="Set environment variables and pull the image">
    Choose an image tag and set the public URL to the address remote browsers and CLI clients will use to reach the Web UI. The Compose file does not substitute a misleading localhost URL.

    ```bash
    export MOTRIX_IMAGE='docker.io/motrixapp/motrix-server:2.0.0-beta.18'
    export MOTRIX_PUBLIC_URL='http://nas.example.lan:8080'
    docker compose pull server
    ```

    To use GHCR or pin to an immutable digest instead:

    ```bash
    export MOTRIX_IMAGE='ghcr.io/agalwood/motrix-server:2.0.0-beta.18'
    # or pin by digest for maximum reproducibility:
    export MOTRIX_IMAGE='motrixapp/motrix-server@sha256:<manifest-digest>'
    ```
  </Step>

  <Step title="Start the service">
    Start the container and wait for it to report healthy before proceeding.

    ```bash
    docker compose up -d --wait
    docker compose ps
    ```
  </Step>

  <Step title="Read the operator token">
    On first start, Motrix generates a credential at `/data/operator-token` (mode `0600`). With bind mounts, read it directly from the host:

    ```bash
    cat motrix-data/operator-token
    ```

    The same token is reused across restarts and image replacements. Keep it safe — it grants full control over the server.
  </Step>

  <Step title="Open the Web UI and log in">
    Navigate to `http://nas.example.lan:8080` (or the value you set for `MOTRIX_PUBLIC_URL`) in any browser. Enter the operator token when prompted to unlock the interface.
  </Step>
</Steps>

## Named Volumes (Alternative)

Use `compose.named-volumes.yaml` when the NAS should manage storage locations — for example on systems where assigning a numeric UID to a host directory is difficult. Docker initialises both volumes with `1000:1000` ownership automatically, so no `chown` step is needed.

```bash
export MOTRIX_PUBLIC_URL='http://nas.example.lan:8080'
docker compose -f compose.named-volumes.yaml pull server
docker compose -f compose.named-volumes.yaml up -d --wait
```

<Note>
  Do not pass `--volumes` to `docker compose down` when using named volumes — that option deletes them. Bind mounts are usually easier when downloads must also appear in a NAS shared folder.
</Note>

## Docker Run (Equivalent)

This command is equivalent to the bind-mount Compose deployment and uses the same security flags:

```bash
mkdir -p motrix-data downloads
MOTRIX_UID="$(id -u)"
MOTRIX_GID="$(id -g)"
chown "$MOTRIX_UID:$MOTRIX_GID" motrix-data downloads

docker run -d \
  --name motrix-server \
  --init \
  --restart unless-stopped \
  --stop-timeout 120 \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m,mode=1777 \
  --security-opt no-new-privileges:true \
  --user "$MOTRIX_UID:$MOTRIX_GID" \
  -e MOTRIX_PUBLIC_URL='http://nas.example.lan:8080' \
  -e MOTRIX_MDXP_HOST=0.0.0.0 \
  -p 8080:8080 \
  -p 16801:16801 \
  -v "$PWD/motrix-data:/data" \
  -v "$PWD/downloads:/downloads" \
  motrixapp/motrix-server:latest
```

`MOTRIX_MDXP_HOST=0.0.0.0` controls the MDXP listener inside the container. The two `-p` options publish those container ports on the Docker host: port 8080 for the Web UI and port 16801 for the MDXP client endpoint.

## Network Publication Modes

The listeners inside the container and the ports published on the Docker host are separate boundaries. The Web/API process listens on `0.0.0.0:8080` inside the container, and the Compose file sets the internal MDXP listener to `MOTRIX_MDXP_HOST=0.0.0.0` on port 16801. Those container-wide listeners let Docker forward traffic; they do not by themselves make either service public.

The standard direct-LAN configuration keeps the existing defaults: both host ports bind to `0.0.0.0`, so trusted LAN devices can reach the Web service on 8080 and MDXP on 16801. The publication controls are independent:

| Compose variable | Controls | Default and fallback |
|------------------|----------|----------------------|
| `MOTRIX_WEB_BIND_IP` | Host address publishing container port 8080 | `MOTRIX_BIND_IP`, then `0.0.0.0` |
| `MOTRIX_MDXP_BIND_IP` | Host address publishing container port 16801 | `MOTRIX_BIND_IP`, then `0.0.0.0` |
| `MOTRIX_BIND_IP` | Compatibility fallback for both services | `0.0.0.0` |

Do not change `MOTRIX_MDXP_HOST` to `127.0.0.1`: that loopback belongs to the container, so Docker port forwarding and other containers cannot reach it.

### Reverse Proxy on the Docker Host

The included `compose.reverse-proxy.env` binds both published origin ports to the Docker host's loopback. It is intended for a reverse proxy running on that host:

```bash
export MOTRIX_PUBLIC_URL='https://motrix.example.com'
docker compose --env-file compose.reverse-proxy.env -f compose.yaml up -d --wait
```

Configure the host proxy with separate upstreams for `127.0.0.1:8080` (Web UI/API) and `127.0.0.1:16801` (MDXP HTTP and SSE), and preserve cookies, authorization headers, and streaming responses.

### Reverse Proxy in Another Container

When the proxy is a container on the same user-defined Docker network, omit `ports` from the Motrix service entirely. Route the proxy to `server:8080` and `server:16801` over that private network, and publish only the proxy's TLS entry point. Keep both internal listeners on `0.0.0.0` so the proxy container can reach them.

## Synology DSM 7 Container Manager

DSM labels can vary slightly between Container Manager updates, but the deployment model is the same:

1. Install **Container Manager** from Package Center.
2. In File Station, create a project directory such as `/volume1/docker/motrix`, with `motrix-data` and `downloads` below it. You may instead make `downloads` a separate shared folder and replace the left side of that bind mount in `compose.yaml` with its absolute path.
3. Choose a dedicated, non-administrator DSM account. Determine its numeric UID/GID with `id <account>` over an administrator SSH session, then give that numeric owner write access to both directories. Set `MOTRIX_UID` and `MOTRIX_GID` to the same values. DSM ACL access alone does not repair a mismatched Unix owner inside every container setup.
4. In **Container Manager > Project**, create a project using that directory and import or paste `compose.yaml`. Set `MOTRIX_PUBLIC_URL` to the browser URL that other devices will use, for example `http://nas-name:8080`. Set any changed ports or UID/GID values in the Project environment.
5. Build/start the Project. Container Manager should pull `motrixapp/motrix-server:latest`; it must not display a local image build.
6. Wait for the service to become healthy, open the Web URL, and read `motrix-data/operator-token` from an administrator shell to unlock it.

Do not enable "high privilege", mount the Docker socket, or grant access to the whole NAS filesystem. If DSM's reverse proxy runs in the host network context, use `compose.reverse-proxy.env` so both origins bind to host loopback.

## fnOS Docker/Compose

On fnOS, install Docker from the app store, then use its Compose/Project view:

1. Create an application directory with separate `motrix-data` and `downloads` directories in Files. Do not put either directory on temporary container storage.
2. Give both directories to a dedicated non-root numeric UID/GID. Use those numbers for `MOTRIX_UID` and `MOTRIX_GID`; do not work around a mismatch by running as root.
3. Create a Compose project from `compose.yaml`. The relative mounts resolve below the selected project directory. If fnOS only accepts pasted YAML, replace `${...}` entries with the desired literal values or add the same values through its environment editor.
4. Use `motrixapp/motrix-server:latest` for stable automatic upgrades, or an immutable SemVer tag for controlled upgrades. Docker chooses `amd64` or `arm64` from the manifest.
5. Set `MOTRIX_PUBLIC_URL`, verify ports 8080 and 16801 are not already used, start the project, and wait for the health status before opening the Web UI.

fnOS share permissions and the container's Unix UID/GID must both allow writes. If downloads appear in the container but not in Files, inspect the left-hand bind path and confirm it points to the intended fnOS storage pool.

## Pairing the CLI Client

Remote CLI and agent clients connect through a device-code pairing flow. The client displays a short code, and the operator approves it in the Web UI. Once paired, the client stores a long-lived credential and reconnects automatically.

```bash
motrix pair --name my-nas
# Follow the prompts in your terminal.
# When instructed, approve the code in the Motrix Web UI.
motrix list
```

If the Web UI is temporarily unreachable, an SSH operator can approve the exact code from inside the running container without exposing any additional port:

```bash
# List pending pairing requests
docker compose exec server motrix-admin pairing pending

# Approve a specific device code
docker compose exec server motrix-admin pairing approve ABCD-EFGH

# Deny a request
docker compose exec server motrix-admin pairing deny ABCD-EFGH
```

Start the pairing request on the client first, then enter the code shown by the client. There is intentionally no approve-all or remote-endpoint argument.

## Upgrade and Rollback

<Steps>
  <Step title="Back up application data">
    Stop the service cleanly so that SQLite and the aria2 session are consistent, create a timestamped archive of the data directory, then restart before the upgrade.

    ```bash
    docker compose stop server
    tar -C . -czf "motrix-data-$(date +%Y%m%d).tar.gz" motrix-data
    docker compose start server
    ```
  </Step>

  <Step title="Pull the new image and replace the container">
    ```bash
    docker compose pull server
    docker compose up -d --wait
    docker compose ps
    ```

    The two mounts, generated operator token, downloads, aria2 session state, and installed plugins are all preserved.
  </Step>

  <Step title="Roll back if needed">
    Set `MOTRIX_IMAGE` to the previous immutable tag or digest and recreate the service. If the newer version migrated persistent state, restore the matching `/data` backup before starting the older image.

    ```bash
    export MOTRIX_IMAGE='docker.io/motrixapp/motrix-server:2.0.0-beta.17'
    docker compose up -d --wait
    ```

    Do not assume an older binary can read state written by a newer release. Always restore from the backup that matches the image you are rolling back to.
  </Step>
</Steps>

## Health Check and Diagnostics

`GET /healthz` is public and only returns success after the HTTP service and aria2 are both ready. The `/api/diagnostics` endpoint requires the operator token and reports engine status, effective storage paths, allowed download roots, runtime UID, plugin status, and FFmpeg detection.

```bash
TOKEN="$(cat motrix-data/operator-token)"

# Public health probe
curl --fail http://127.0.0.1:8080/healthz

# Detailed diagnostics (requires operator token)
curl --fail \
  --header "Authorization: Bearer ${TOKEN}" \
  http://127.0.0.1:8080/api/diagnostics

# Tail container logs
docker compose logs --tail=200 server
```

## Troubleshooting

| Symptom | Check and correction |
|---------|----------------------|
| Pull returns 404 or `manifest unknown` | Confirm the repository/tag spelling and that an image-bearing release exists. Try the same immutable tag on the other registry (Docker Hub or GHCR); do not substitute a similarly named third-party image. |
| `no matching manifest` | Confirm the NAS is 64-bit `amd64` or `arm64` with `docker info`; 32-bit ARM is unsupported. |
| Startup reports `EACCES`, read-only, or a path failure | Compare `docker inspect ... .Config.User` with numeric ownership of both mounts. Correct ownership/ACLs; do not run privileged or as root. |
| Port is already allocated | Change `MOTRIX_HTTP_PORT` or `MOTRIX_MDXP_PUBLIC_PORT`, and update `MOTRIX_PUBLIC_URL` if the Web port changes. |
| Web UI opens but unlock fails | Read the current persistent `/data/operator-token`; do not use a token copied from another deployment. Verify the file is regular, base64url text, and mode `0600`. |
| Download directory is rejected or files are missing from the NAS share | Use an absolute container path below `MOTRIX_ALLOWED_SAVE_DIRS`; verify the intended host directory is mounted at that exact path and writable by the runtime UID/GID. |
| Plugin install fails | Inspect `/api/diagnostics` and logs, retain `/data`, confirm package/source trust and network/TLS access, and mount any `MOTRIX_PLUGIN_IMPORT_DIRS` explicitly. Do not enable unmanaged plugins for a normal `.moext`, URL, or registry install. |
| Container is unhealthy after an upgrade | Inspect logs and diagnostics, verify both mounts, then roll back to the recorded immutable image and matching `/data` backup. |

<Warning>
  Never run the container as root (UID 0) or with privileged mode. Always set proper ownership on mount directories to match the runtime UID before starting the service. A mount permission error is corrected by fixing ownership — not by escalating the container's privileges.
</Warning>
